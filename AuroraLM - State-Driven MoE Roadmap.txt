AuroraLM - State-Driven MoE Roadmap

AuroraLM is not meant to be a generic chatbot with an emotion prompt pasted on
top. The aim is a voice whose routing and internal representation can receive
Aurora's live cognitive state as a real input.

The state driver is a **171-dimensional emotional vector space**. The model
should learn from it, while Aurora's existing memories, comparators, oath, and
world model remain the mind around the voice.

The orchestrator now captures each processed turn as a lossless JSONL record:
input, exact response or silence, regulators, scored active nodes, and the raw
171-dimensional state vector. Aurora and AuroraLM use the same emotion ordering
and schema fingerprint, and a captured record is accepted directly by
`AuroraState171.from_record`.

The session logger now emits the exact canonical 11-regulator vector in model
order and validates every value against its configured range. Prediction bias,
retrieval score, and the categorical PFC label remain available as separate
telemetry rather than being mislabelled as model regulators. `dataset.py`
revalidates the same exact contract before a turn can enter stateful training.

The three-file orchestrator change is verified on the local-only Aurora
checkpoint `741ce9c` (`agent.py`, `session_logger.py`, and `test_recovery.py`).
Aurora's documented private Python suite passes all 109 tests at that
checkpoint. The checkpoint has not yet been merged into `dev` or pushed, so
the mechanism is complete and tested locally while repository integration
remains pending.

`moe_router.py` and `experts.py` now provide the untrained MoE mechanics behind
an optional 8-expert, top-2 `MOE_PILOT` configuration. Routing remains
token-led; Aurora's state prior is accepted but has zero routing influence
until Gate 2 is cleared. Expert capacity is isolated per sample and allocated
in causal token order, with explicit overflow fallback so future tokens cannot
change earlier outputs and no token silently loses its feed-forward branch.
Dense SwiGLU weights can be cloned into every expert to preserve the dense
function at MoE initialisation. Seventeen focused tests cover routing, dispatch,
gradients, overflow, causal masking, dense equivalence and telemetry.

`dataset.py` now builds deterministic, hashed train/validation data from
explicitly allowlisted sources. It keeps clean documents, legacy unverified
turns, and exact state-aligned turns in separate files; excludes embeddings,
raw fragments, backups, live state, and Minecraft logs; and writes only beneath
git-ignored data directories. The Aurora-only v1 build is preserved. The mixed
`aurora_smollm_v1` build contains 10,787 deduplicated documents (9,664 train,
1,123 validation), 903 quarantined legacy turns, and 10,988 train-split
tokenizer texts. Verified stateful turns will accumulate as Aurora runs with
the new recorder.

`smollm_sampler.py` reproducibly samples the public
`HuggingFaceTB/smollm-corpus` dataset at revision
`3ba9d605774198c5868892d7a8deda78031a781f`. The bounded local sample contains
7,500,398 FineWeb-Edu-Dedup tokens across 7,422 documents and 2,000,392
Cosmopedia-v2 tokens across 2,489 documents. The sampler records selected row
indices, content hashes, source metadata, and ODC-By attribution in its
manifest; the downloaded data remains outside Git.

`tokenizer.py` is a byte-level BPE implementation with an exact PILOT
vocabulary contract (`vocab_size=8192`) and fixed special-token IDs:
`<pad>=0`, `<bos>=1`, `<eos>=2`, `<unk>=3`. The full byte alphabet makes
unseen UTF-8 text representable without unknown-token loss.

The final artifact has been trained once on the mixed corpus and frozen at
`artifacts/aurora_bpe_8192_v1`. Its fingerprint is
`45cc10034fb48082d8c997c25a18a6d15f00f4b7335a231a1acdcf282030f14e`.
An independent retraining produced byte-for-byte identical tokenizer JSON.
Training, inference, and checkpoints must load this artifact and reject any
different fingerprint. Raw JSON, embedding arrays, and metadata remain
excluded so they cannot consume BPE merge capacity.

`train.py` now implements the dense PILOT language-pretraining stage with
neutral state (`aurora_state=None`). It packs document tokens into overlapping
512-token causal blocks, keeps the manifest-defined train/validation split,
uses deterministic shuffled batches, cosine learning-rate decay with warmup,
AdamW, gradient clipping, optional AMP, periodic validation, a live
loss/throughput/ETA progress bar, verified checkpoint initialization for new
optimization phases, and atomic checkpoint/resume. Checkpoints bind the full
model configuration, runtime
versions, tokenizer fingerprint, dataset hashes, state-schema fingerprint,
packed-data statistics, optimiser/scaler state, sampler position, and RNG
state. Legacy unverified turns and raw state data are not used in this stage.

The complete mixed corpus packs into 19,216 train blocks from 9,838,809 tokens
and 2,032 validation blocks from 1,040,605 tokens. An interrupted tiny training
run resumed tensor-for-tensor identically to an uninterrupted run. A disposable
one-step CPU run also passed through the real 9,994,960-parameter PILOT model,

A real local CPU run, `pilot_dense_local_i5_v1`, completed on the i5-3470 in

The second controlled base-pretraining phase,
`pilot_dense_local_i5_phase2`, completed another 5,000 steps from that verified
checkpoint with a fresh optimiser and a lower `1e-4` peak learning rate.
Validation loss improved from 5.1240 to 4.9653 and perplexity from 168.01 to

A checkpoint-contract regression confirms that the phase can resume without

`readiness_gate.py` is the hard interlock before state-conditioned work. Gate 1
requires a completed candidate run, a non-regressing validation result, no
material improvement over the final five evaluations, and a completed blinded
semantic scorecard. Loss alone cannot approve the base. Gate 2 independently
requires genuine exact-turn text/state pairs in both train and validation,
multiple distinct 171-vectors, a manifest-matching state file, and a positive
`ACTIVATION_CEILING` backed by a privacy-safe calibration receipt. The audit
also verifies every candidate training state against the frozen ceiling without
clipping. It never runs the correct-vs-shuffled ablation itself.

The completed audit gives Gate 1 a quantitative pass: the run finished, beats
the phase-one validation result, and meets the plateau criterion. Its formal
status remains `PENDING` only because the blinded semantic scorecard is not
complete. All 18 qualitative generations were produced; sampled and
conservative decoding avoid most repetition, but inspection still shows weak
prompt retention, clause coherence, factual stability, and code structure.
The activation sub-gate is now calibrated from 59 genuine schema-compatible
captures (205 positive node scores across 14 session logs). The maximum
observed activation, `0.78`, is frozen with no silent clipping; its tracked
aggregate receipt contains schema and source digests but no conversation text.
Gate 2 remains `BLOCKED` because the canonical dataset still contains zero
post-fix, 11-regulator state-aligned turns. Therefore state conditioning and
the state ablation remain explicitly unauthorised; only dense base pretraining
may proceed.

`inference.py` now verifies the checkpoint pointer and SHA-256, runtime versions,
model configuration, tokenizer fingerprint, state schema, tensor shapes, and
finite weights before generation. It supports deterministic greedy, top-k, and
nucleus sampling with temperature, repetition penalty, context truncation, and
EOS handling. The qualitative harness records repetition metrics and can audit
generated 16-word shingles against the training documents without reporting
source text.

At step 5,000, sampled continuations have recognisable English syntax but weak

language signal but is not yet ready to serve as Aurora's voice; continue base
pretraining and reevaluate before instruction or state-conditioned tuning.

## Next is the important bit: `state_schema.py`

This is where Aurora's 171-dimensional state driver becomes a stable interface
instead of a loose list of numbers.

```text
Aurora live state
        |
        v
171 emotional vector values
        |
        v
normalise + validate + version
        |
        v
AuroraState171
```

Define, in one place:

- the ordering and names of all 171 dimensions;
- normalisation ranges and missing-value behaviour;
- the sampling time for each generation turn;
- a schema version saved with every training example and checkpoint.

The old `state_size=16` can remain as a **learned compressed latent**, but it
must not silently replace the 171-value source state.

## Then: `state_encoder.py`

```text
AuroraState171
        |
        v
StateEncoder
        |
        +--> compact state latent -> adaptive layer norm in every block
        |
        +--> routing/cache prior -> keeps relevant expert pools warm
```

This is the bridge between Aurora's internal state and an MoE design. The
encoder may compress 171 values to a smaller latent, but it should preserve a
traceable mapping back to the source state for experiments and debugging.

## The MoE brain block

```text
RMSNorm
  -> attention
  -> residual
  -> RMSNorm
  -> token router + Aurora state prior
  -> top-k experts
  -> residual
```

Start small: **8-16 experts with top-2 routing**. The token router remains the
final authority over which experts execute. Aurora's state should initially
affect only the cache/prefetch priority and a bounded routing prior.

That means Aurora can make relevant specialist pools warm without hard-forcing
experts or overriding what the language context requires.

## The experiment that matters

Train and compare four conditions on the same held-out work:

```text
1. No state                     control
2. Correct Aurora state         intended condition
3. Shuffled Aurora state        tests whether the state signal is real
4. State-aware cache only       tests speed without changing routing quality
```

Measure more than loss:

- state-appropriate generation under fixed prompts;
- expert-routing and cache-hit changes by emotional state;
- response latency and disk reads;
- stability of Aurora's safety and withdrawal signals;
- blind human ratings of coherence and state fit.

General corpus samples must not always use zero state while Aurora journal
samples always use real state. Mix, shuffle, and control the data so the model
cannot merely learn the source of the text.

## Compute ladder

```text
PILOT   -> verify the 171-state mechanism on a tiny MoE
SMALL   -> repeat with real routing telemetry on rented GPU time
COLIBRI -> use the evidence to guide expert warming/pinning experiments
FULL    -> only after the ablations show a reliable effect
```

Do not spend cloud credits on FULL training until PILOT proves that correct
state beats shuffled state and the cache policy produces a measurable benefit.

## Relationship to Colibri

AuroraLM and Colibri are complementary, not the same project:

- **AuroraLM** tests whether Aurora's state can inform routing in a small,
  trainable MoE.
- **Colibri** is the large-model runtime where an evidence-backed state profile
  can guide expert warming, pinning, and prefetching.

The first Colibri integration should be a state-labelled cache profile, not a
hard override of its native expert router.

## The hand-off to Aurora

AuroraLM remains a swappable voice behind `llm_interface.py`.

```text
Aurora's cognitive systems
        -> AuroraState171
        -> StateEncoder / model adapter
        -> AuroraLM or Colibri-backed voice
        -> response
```

Her identity does not live in the weights alone. The model is an organ; the
state driver, memories, comparators, and oath remain the wider system that
gives that organ a context.
